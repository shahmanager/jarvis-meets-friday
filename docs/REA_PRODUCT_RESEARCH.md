# Public agent product research: Grok Bot and Meta Muse

Research snapshot: 16 October 2026. This note distinguishes vendor-published product descriptions from static client evidence and from this repository's implementation. It is a design reference, not a benchmark or parity claim.

## What the public sources describe

**Grok Bot** is presented as a persistent, named agent with its own task context, memory, skills and routines, operating on a persistent cloud computer. Bots can collaborate, and their computer, browser sessions, files and connected logins are shared within the account; separate Bot identities or screens are therefore not separate security boundaries. The product exposes progress, tool activity and artifacts in the conversation, supports user steering during work, and leaves some actions for approval or human takeover. Its docs recommend first making a task reliable, then saving the procedure as a Skill, and only then scheduling it as a Routine. These are xAI's descriptions of the product, not independent observations. See [Grok Bot overview](https://docs.x.ai/grok-bot/overview), [Bots](https://docs.x.ai/grok-bot/bots), [collaboration](https://docs.x.ai/grok-bot/chat-and-collaboration), [computer and apps](https://docs.x.ai/grok-bot/computer-and-apps), [skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations), and [approvals and security](https://docs.x.ai/grok-bot/approvals-security-and-privacy).

**Muse** is Meta's personal-agent product, distinct from the Muse Spark model/API. Meta describes a persistent per-user Secure VM and browser, chosen app connectors, long-running/background goals, proactive suggestions, interruption/steering, reviewable artifacts, and per-connection access controls. The product pages say users approve consequential actions (including sending and purchases), can inspect an audit trail, adjust or disconnect access, and can ask Muse to forget remembered details. Meta also describes separate security services: an agent runtime isolated from credentials and the permission/network authority, with scoped connector execution. Those are vendor descriptions of the launch design. The safety write-up provides more detail, including a Linux runtime container and an external Sentinel authority; it is a product architecture disclosure, not verified source code. Meta's [launch announcement](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent) directly links `muse.ai` as the web launch surface and `introducing.muse.ai` as the design article; the latter also links back to Muse and carries a Meta copyright line. See [Muse](https://ai.meta.com/muse/), [How We Designed Muse](https://introducing-muse.com/), and [How We Built Safety Into Muse](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse).

Meta separately describes Muse Spark model capabilities such as multimodal reasoning and multi-agent orchestration. A model announcement does not establish that every capability is present in every Muse client surface or account. See [Introducing Muse Spark](https://about.fb.com/news/2026/04/introducing-muse-spark-meta-superintelligence-labs/) and [Muse Spark 1.1](https://ai.meta.com/blog/introducing-muse-spark-meta-model-api/).

## Patterns worth carrying into this project

- Keep task identity and durable task state beyond a single model turn. Make status, approvals, task chat, results and artifacts visible as a coherent work history. This repository already persists tasks and events, shows delegated `waiting_peer` state, and returns artifacts; improve those paths from measured user tasks rather than cloning a competitor's UI.
- Let users steer or stop active work, and show what already happened. Grok's docs explicitly note that stopping does not undo completed effects; Muse's design describes interruption and concurrent task entry. The dashboard should preserve the distinction among stopped, cancelled, completed, and uncertain external effects.
- Separate reusable procedures from recurring triggers. First validate a repeatable workflow, then turn it into a skill, and schedule only after its inputs, outputs, error behavior and approval gates are clear. This fits the existing roadmap's recommendation to measure before expanding automation.
- Keep the permission authority outside model-authored plans and tool descriptions. Meta's disclosed Sentinel split is a useful boundary pattern; this project already makes grants and approvals deterministic in the Worker. A cloud-hosted Codex app-server does not inherit the security properties of Muse's per-user VM or Grok's account-shared cloud computer, and should not be presented as equivalent.
- Show reviewable outputs and evidence, with clear status for work underway and action awaiting approval. Both products emphasize artifacts/action history; this repo has persisted events, source-linked search results, approvals and downloadable artifacts that can support that pattern.

These are transferable product patterns, not recommendations to add every feature. In particular, proactive background actions, broad connectors, or persistent memory increase the need for narrow grants, cancellation, observable outcomes and deletion/revocation behavior.

## REA client inspection and limits

I used the pinned npm release `rea-agents@6.5.0` in ignored `work/rea-research` with install scripts disabled; nothing was installed globally, added to runtime dependencies, or vendored. REA's documented website workflow can passively inspect a Chrome-family browser over loopback CDP and statically analyze captured scripts. Its docs warn that selected accessibility text, script source, URL query values and some console text can contain secrets, and that attaching CDP can affect browser state. See [REA README](https://github.com/morluto/rea) and [browser observation guide](https://github.com/morluto/rea/blob/main/docs/browser-observation.md).

For a bounded check, I fetched the public HTML for `grok.com` and `muse.ai`, selected the first 20 script references listed by each page, fetched those public HTTPS resources from the Grok CDN or Muse origin, and ran REA's static JavaScript application analyzer on the files. Meta's launch announcement links to `muse.ai`, and the fetched page title describes “Muse — Your Personal AI Agent”; this attribution is not based on the domain name alone. The HTML listed 106 Grok and 43 Muse script references; the 20-file samples are incomplete. REA produced partial graphs (66 nodes/67 edges for the Grok sample; 90 nodes/93 edges for Muse) and explicitly notes that static imports, endpoints, storage, and routes do not prove execution. The analysis did not execute either application, inspect authenticated pages, or observe user actions. The Muse URL redirected to an authentication URL in web browsing; I did not access it. The small partial samples did not establish a meaningful client-side agent architecture, so no client-only claim above depends on them.

I did not attach REA to an existing browser, use an account, inspect private endpoints, invoke app actions, or send captured data to a model provider. The static samples and REA installation remain in ignored `work/rea-research`; no REA code is vendored, so no REA license file is needed in this repository. A fuller client study would require a disposable profile, exact public-origin allowlisting, a fresh capture of the needed app state, and explicit minimization/review of script and URL evidence before sharing it with any model.

## Unknowns

Public docs cannot establish the products' actual implementation, authorization correctness, reliability, model routing, memory-write policy, retention details beyond published statements, or behavior across account and rollout variants. These product pages and security posts are vendor-authored descriptions. The sampled bundles are partial and their source maps were not fetched; no dynamic task was run. No reproducible task-quality, latency, cost, safety, or parity evaluation was performed. The repository's own docs remain authoritative for what this project currently implements; see [architecture](architecture.md), [capabilities](CAPABILITIES.md), and [remaining work](REMAINING_WORK.md).
